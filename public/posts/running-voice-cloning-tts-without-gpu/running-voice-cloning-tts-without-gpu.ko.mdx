## GPU 없이 Voice Cloning TTS 운영하기

짧은 레퍼런스 음성으로 새로운 목소리를 만드는 Voice Cloning은 예전부터 관심을 두던 분야였습니다. 하지만 서비스를 직접 운영하려고 하면 모델 성능보다 GPU 비용과 배포 구조를 먼저 고민하게 됩니다.

사용자가 목소리를 하나 추가할 때마다 모델을 다시 학습해야 한다면, 목소리 수만큼 GPU 작업과 전용 가중치가 늘어납니다. 합성할 때도 GPU가 필요하면 요청이 없는 동안에도 자원을 유지하거나 매번 콜드 스타트를 감수해야 합니다.

이번에는 이 구조를 조금 다르게 만들고 싶었습니다.

`목소리를 만들 때도 GPU를 사용하지 않고, 완성된 목소리는 작은 CPU 서버에서 계속 호출할 수 없을까?`

실험 끝에 Supertonic 3의 custom voice JSON을 CPU에서 만들고 Oracle Cloud의 ARM64 서버에 여러 목소리를 이름으로 등록해 합성하는 구조까지 연결했습니다. 이후에는 같은 레퍼런스로 Audio8의 zero-shot Voice Cloning도 구성해 두 방식의 화자 유사도와 CPU 성능을 비교했습니다.

## Supertonic TTS란

![31개 언어와 CPU 기반 on-device 합성을 지원하는 Supertonic 3 소개 이미지](/public/posts/running-voice-cloning-tts-without-gpu/supertonic-3-overview.png)

[Supertonic](https://github.com/supertone-inc/supertonic)은 Supertone이 공개한 on-device 다국어 TTS입니다. ONNX Runtime에서 추론하도록 배포되어 무거운 서버 프레임워크가 필요 없습니다. Python은 물론 브라우저와 모바일처럼 GPU가 없는 환경에서도 실행됩니다.

이 글에서 사용한 Supertonic 3는 약 9,900만 개의 parameter로 31개 언어를 지원하고 44.1kHz 음성을 출력합니다. 공식 모델에는 남성 5개와 여성 5개, 모두 10개의 voice가 들어 있습니다. 제가 특히 마음에 든 건 모델 크기보다 voice와 합성 모델을 분리한 구조였습니다. 하나의 TTS 모델을 그대로 두고 작은 voice style만 바꾸면 여러 목소리를 낼 수 있습니다. 자세한 모델 사양과 지원 범위는 [공식 README](https://github.com/supertone-inc/supertonic#readme)와 [Supertonic 3 모델 카드](https://huggingface.co/Supertone/supertonic-3)에 나와 있습니다.

공식 [Python SDK](https://supertone-inc.github.io/supertonic-py/)에는 로컬 서버도 들어 있습니다. 모델을 내려받아 `supertonic serve`를 실행하면 CPU 기반 TTS API가 열리고 별도로 만든 custom voice JSON도 같은 런타임에 불러올 수 있습니다. 특정 클라우드나 GPU에 묶이지 않는 형태였습니다.

## Audio8 TTS란

[Audio8 TTS](https://github.com/Audio8-AI/Audio8_TTS)는 레퍼런스 음성과 전사를 직접 참고해 새 문장을 말하게 만드는 zero-shot Voice Cloning 모델입니다. 이 글에서는 CPU 배포를 목표로 공개된 [0.1B ONNX INT8 모델](https://huggingface.co/Audio8/audio8-TTS-0.1B-ONNX-INT8)을 사용했습니다.

핵심은 Neural Audio Codec과 DualAR 구조입니다. Neural Audio Codec은 긴 파형을 그대로 다루는 대신 음성을 작은 코드 묶음으로 압축합니다. DualAR은 먼저 문장의 내용과 흐름을 담당하는 큰 단위의 코드를 만들고, 이어서 음색과 세부 소리를 채우는 코드를 생성합니다. 레퍼런스에서 뽑은 음성 코드를 조건으로 사용하므로 원래 화자의 특징을 비교적 직접적으로 따라갈 수 있습니다.

대신 코드를 앞에서부터 하나씩 생성해야 합니다. 여러 음성 구간을 한꺼번에 처리하는 Supertonic보다 화자 유사도에는 유리하지만 CPU에서는 시간이 오래 걸릴 수 있습니다. 후반부의 음질과 속도 차이는 이 구조에서 시작됩니다.

## Voice Builder 종료 공지에서 시작된 문제

Supertonic에도 공식 custom voice 제작 도구인 Voice Builder가 있었습니다. 짧은 레퍼런스 음성을 넣어 Supertonic 버전에 맞는 voice JSON을 만든 다음, 내려받은 파일을 로컬 런타임에 불러오는 방식이었습니다.

그런데 2026년 7월 23일 [공식 저장소에 운영 종료가 공지](https://github.com/supertone-inc/supertonic#notice)됐습니다. 저장소에 대한 공식 지원이 종료되고, Voice Builder도 2026년 8월 31일 이후에는 접근할 수 없게 됩니다. 이미 내려받은 JSON은 계속 사용할 수 있지만 새로운 목소리를 만드는 공식 경로는 더 이상 지속 가능한 선택지가 아니었습니다.

운영 중인 TTS의 목소리 추가 기능이 외부 웹 도구 하나에 의존하면, 서버가 살아 있어도 voice 제작 파이프라인은 멈출 수 있습니다. 그래서 Voice Builder와 같은 출력물을 직접 만드는 방법을 찾기 시작했습니다.

## Supertonic은 어떻게 음성을 만드는가

[SupertonicTTS 논문](https://arxiv.org/abs/2503.23108)에 따르면 모델은 세 부분으로 이뤄집니다.

1. 음성을 작은 표현으로 압축하고 다시 소리로 복원하는 장치(speech autoencoder)
2. 입력 문자를 압축된 음성 표현으로 바꾸는 생성기(flow-matching 모델)
3. 문장을 얼마나 길게 말할지 정하는 예측기(duration predictor)

간단히 말하면 먼저 문장의 재생 시간을 정하고, 그 길이에 맞는 압축 음성을 만든 다음, 마지막에 우리가 듣는 파형으로 복원합니다. 중간 표현을 작게 유지하고 여러 구간을 함께 처리하기 때문에 작은 모델에서도 합성이 빠릅니다.

![문자 입력과 voice JSON의 style_dp·style_ttl이 duration predictor와 flow matching을 거쳐 44.1kHz 음성으로 합성되는 Supertonic 3 구조](/public/posts/running-voice-cloning-tts-without-gpu/supertonic-inference-pipeline.svg)

custom voice JSON은 전체 모델을 복사한 파일이 아닙니다. [공식 SDK의 custom voice 사용법](https://supertone-inc.github.io/supertonic-py/quickstart/)과 [공개된 voice style 파일](https://huggingface.co/Supertone/supertonic-3/tree/main/voice_styles)을 보면, 두 개의 tensor를 `data`와 `dims`로 나눠 저장합니다.

```json
{
  "style_dp": {
    "data": ["... 128개의 실수 ..."],
    "dims": [1, 8, 16]
  },
  "style_ttl": {
    "data": ["... 12,800개의 실수 ..."],
    "dims": [1, 50, 256]
  }
}
```

`style_dp`는 128개 값으로 duration predictor에 들어가고 `style_ttl`은 12,800개 값으로 text-to-latent 경로를 조건화합니다. 이 연결은 [공식 Supertonic 구현](https://github.com/supertone-inc/supertonic)에도 나옵니다. 전자는 발화 길이와 리듬에, 후자는 합성되는 음색과 발화 특성에 영향을 줍니다. 그렇다고 둘을 독립적인 의미 벡터로 단순화하기는 어렵습니다. 최종 목소리는 두 tensor와 입력 문장, 합성 설정이 함께 결정합니다.

운영 관점에서는 다음처럼 나눌 수 있습니다.

```text
1회성 Voice Cloning
reference audio
  -> voice style 탐색
  -> custom_voice.json

반복 TTS
custom_voice.json + text
  -> Supertonic 3 ONNX runtime
  -> audio
```

이 JSON 포맷을 그대로 만들 수 있다면 ONNX 모델을 목소리마다 복사하거나 전용 서버를 띄울 필요가 없습니다. 첫 번째 단계 역시 모델 전체를 Fine-tuning하는 대신, 고정된 Supertonic 안에서 레퍼런스와 가까운 style 값을 찾는 문제로 바꿀 수 있습니다.

## 처음에는 모델을 학습해야 한다고 생각했다

처음에는 레퍼런스 음성을 기준으로 Supertonic의 voice embedding을 최적화하는 프로젝트들을 검토했습니다. 레퍼런스의 대본으로 음성을 다시 합성해 원본과 가까워지도록 embedding을 수정하거나, `ECAPA`나 `WavLM` 같은 speaker encoder로 두 음성의 유사도를 계산하는 방식이었습니다.

실행 자체는 가능했습니다. Modal의 GPU 환경에서 레퍼런스를 전처리하고 수백 번에서 수천 번 최적화해 Supertonic 3용 JSON까지 만들었습니다.

하지만 실제로 들어보면 문제가 분명했습니다.

- 레퍼런스는 남성인데 결과가 여성에 가깝게 나오는 경우가 있었습니다.
- 화자 유사도 점수는 올라가도 사람 귀에는 크게 비슷하지 않았습니다.
- 특정 체크포인트에서는 음색이 조금 가까워졌지만 기계음이 함께 늘었습니다.
- 레퍼런스의 언어와 전사 결과에 따라 출발점이 흔들리는 방식도 있었습니다.

처음에는 학습 횟수를 더 늘리면 해결될 것이라고 생각했습니다. 여러 체크포인트를 같은 문장으로 비교해보니 횟수만의 문제는 아니었습니다. 화자의 어떤 특징을 기준으로 삼고, Supertonic이 표현할 수 있는 목소리 중 어디까지 비교할지가 더 중요했습니다.

이때부터 질문을 바꿨습니다.

`모델 전체를 다시 학습해야 하는가?`

`아니면 이미 학습된 Supertonic 안에서 레퍼런스와 가까운 style만 찾으면 되는가?`

## 화자 특징으로 voice style을 역으로 찾기

마지막에 선택한 방법은 레퍼런스의 화자 특징을 먼저 요약하고, 그 특징과 가장 가까운 Supertonic 목소리를 찾는 방식입니다.

흐름은 이렇습니다.

1. 레퍼런스 음성에서 화자를 구분하는 특징을 추출합니다.
2. 그 특징을 바탕으로 첫 번째 custom voice 후보를 만듭니다.
3. 후보 목소리로 짧은 문장을 실제 합성합니다.
4. 합성 결과가 레퍼런스와 얼마나 가까운지 비교합니다.
5. 더 나은 후보를 만들고 같은 과정을 반복합니다.

```text
reference audio
  -> 화자 특징 요약
  -> custom voice 후보 생성
  -> Supertonic으로 짧은 문장 합성
  -> reference와 비교
  -> 후보 개선
  -> custom voice JSON
```

여기서 Qwen은 최종 음성을 만드는 모델이 아니라 레퍼런스와 합성 후보를 비교하는 “귀”로 사용됩니다. 실제 서비스 음성은 처음부터 끝까지 Supertonic 3가 생성합니다.

후보를 만드는 데는 PCA와 CMA-ES를 사용했지만, 원리는 어렵지 않습니다. 모델을 새로 학습하는 대신 기존 모델로 여러 후보를 만들어 직접 들어보고 가장 가까운 값을 남깁니다. 무거운 학습 과정이 없기 때문에 CPU에서도 실행할 수 있었습니다.

레퍼런스의 정확한 대본도 필요하지 않았습니다. 일본어 레퍼런스로 style을 만든 뒤 한국어 문장을 합성할 수도 있습니다. speaker feature를 찾는 단계와 Supertonic에 새 문장을 입력하는 단계가 분리되어 있기 때문입니다.

## 목소리는 한 번 등록하고 이름으로 호출하기

CPU에서 실행되더라도 voice cloning과 실시간 요청 처리를 같은 서버에 넣을 필요는 없었습니다. 두 작업의 생명주기가 다르기 때문입니다.

- **Voice Cloning:** 목소리 하나를 만들 때만 실행하며 CPU와 메모리를 비교적 많이 사용합니다.
- **TTS serving:** 이미 만들어진 JSON이나 voice profile을 읽고 짧은 요청을 반복해서 처리합니다.

Voice Cloning은 Modal CPU 작업으로 실행하고 결과 JSON이나 voice profile만 내려받았습니다. 실제 TTS 서버는 Oracle Cloud의 Ampere A1 ARM64 인스턴스에 배포했습니다.

![Modal CPU의 1회성 Voice Cloning이 custom voice JSON을 만들고 Oracle ARM64가 이를 반복 TTS 요청에 사용하는 구조](/public/posts/running-voice-cloning-tts-without-gpu/voice-cloning-serving-split.svg)

Supertonic 서버는 `python:3.11-slim` 이미지에 `supertonic==1.3.1`과 ONNX Runtime CPU provider만 설치했습니다. CUDA, PyTorch GPU image와 NVIDIA Container Runtime은 필요하지 않습니다.

초기 운영값은 CPU 2코어와 메모리 4GB로 잡았습니다. 모델 cache와 custom voice는 서로 다른 Docker volume에 저장했고 컨테이너의 root filesystem은 read-only로 두었습니다. 공식 Supertonic 서버에는 인증이 없어서 최소 32자의 API key를 검사하는 ASGI middleware도 추가했습니다.

완성된 JSON은 서버를 다시 빌드하지 않고 API로 등록합니다.

```bash
curl -X POST "https://tts.example.com/v1/styles/import" \
  -H "Authorization: Bearer ${SUPERTONIC_API_KEY}" \
  -F "file=@voices/adam.json"
```

파일명 `adam.json`의 stem인 `adam`이 voice 이름이 됩니다. 이후에는 합성 요청에서 해당 이름만 전달합니다.

```bash
curl -X POST "https://tts.example.com/v1/tts" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${SUPERTONIC_API_KEY}" \
  -d '{
    "text": "안녕하세요. CPU에서 생성한 커스텀 목소리입니다.",
    "voice": "adam",
    "lang": "ko",
    "steps": 5,
    "response_format": "wav"
  }' \
  --output adam.wav
```

여러 JSON을 등록하면 `adam`, `airi`처럼 이름만 바꿔 같은 서버에서 호출하면 됩니다. 같은 이름의 voice를 바꿀 때는 import 요청에 `?overwrite=true`만 추가하면 됩니다.

등록된 JSON은 `/var/lib/supertonic/voices`에 연결된 named volume에 남습니다. 일반적인 image redeploy나 컨테이너 재시작 후에도 자동으로 다시 로드됩니다. 새 목소리 하나를 추가하기 위해 서버를 재배포할 필요가 없는 구조입니다.

그렇다고 volume만 백업으로 여기지는 않았습니다. voice JSON은 다시 만들 수 있더라도 수분의 탐색과 청취 비교를 거친 결과물입니다. 서버 volume과 별도로 암호화된 백업을 두고 JSON 자체는 Git에 올리지 않았습니다.

## 2 step과 5 step 사이에서 고르기

Supertonic은 합성 step을 줄이면 빨라지고 늘리면 품질이 좋아집니다. 같은 목소리로 한 줄, 여러 줄, 문단을 각각 2 step과 5 step으로 반복 생성해 비교했습니다.

2 step은 응답 속도에 유리했지만 긴 문장이나 새로 만든 custom voice에서는 기계음이 더 잘 드러났습니다. 5 step은 시간이 더 걸리는 대신 발음과 음색이 상대적으로 안정적이었습니다. 그래서 현재 운영에서는 5 step을 기본 품질 기준으로 잡고 짧은 미리듣기처럼 지연 시간이 더 중요한 경우에만 2 step을 고려합니다.

공식 문서가 5 step을 반드시 권장하는 것은 아닙니다. SDK 예제와 기본값도 환경에 따라 다르기 때문에 이 값은 직접 청취한 결과를 바탕으로 정한 운영 기준입니다.

## Oracle ARM64에서 Supertonic과 Audio8 비교하기

Supertonic의 목소리 생성부터 등록, 합성 설정까지 정리한 뒤 같은 Oracle 서버에 Audio8 0.1B를 별도 컨테이너로 배포했습니다. Audio8은 CPU 4코어와 메모리 6GB, Supertonic은 CPU 2코어와 메모리 4GB를 사용했습니다. Audio8에는 `top_k=1`과 미리 계산한 레퍼런스 cache를 적용했습니다.

### 실제 응답 속도 비교

등록한 목소리로 한 줄, 여러 줄, 문단을 각각 합성했습니다. 응답 시간은 서버 내부 추론만 잰 값이 아니라 공개 HTTPS endpoint에 요청한 시점부터 완성된 WAV를 받을 때까지의 시간입니다. 따라서 Cloudflare, 네트워크 왕복과 WAV 인코딩도 포함됩니다.

| 모델 | 제한 자원 | 입력 | 응답 시간 | 생성 음성 | RTF | 재생 시간 대비 속도 |
|---|---|---|---:|---:|---:|---:|
| Supertonic 3 | CPU 2 cores · 4GB | 한 줄, 27자 | 3.36초 | 4.74초 | 0.709 | 1.41× |
| Audio8 0.1B | CPU 4 cores · 6GB | 한 줄, 27자 | 14.12초 | 3.20초 | 4.406 | 0.23× |
| Supertonic 3 | CPU 2 cores · 4GB | 여러 줄, 93자 | 6.98초 | 14.07초 | 0.496 | 2.02× |
| Audio8 0.1B | CPU 4 cores · 6GB | 여러 줄, 97자 | 44.56초 | 10.68초 | 4.171 | 0.24× |
| Supertonic 3 | CPU 2 cores · 4GB | 문단, 206자 | 13.87초 | 30.67초 | 0.452 | 2.21× |
| Audio8 0.1B | CPU 4 cores · 6GB | 문단, 215자 | 101.32초 | 22.76초 | 4.452 | 0.22× |

![Oracle ARM64에서 Supertonic 3와 Audio8 0.1B의 한 줄·여러 줄·문단 RTF를 비교한 차트](/public/posts/running-voice-cloning-tts-without-gpu/oracle-arm64-benchmark.svg)

RTF(Real-Time Factor)는 `응답 시간 ÷ 생성된 음성 길이`입니다. 1보다 작으면 재생 시간보다 빠르게 생성했다는 뜻입니다. Supertonic은 문장이 길어질수록 요청 처리 같은 고정 비용이 분산되어 RTF가 0.709에서 0.452까지 낮아졌습니다. 반면 Audio8은 세 입력에서 약 4.2–4.5를 기록했습니다.

차이는 생성 방식에서 나옵니다. Supertonic은 음성 구간을 묶어서 처리하므로 문장이 길어질수록 준비 비용이 나뉘고 RTF가 낮아졌습니다. Audio8은 앞서 설명한 음성 코드를 순서대로 만들어야 하므로 긴 문장에서도 RTF가 약 4.2–4.5에 머물렀습니다. 더 닮은 목소리를 얻는 대신 기다리는 시간이 길어진 셈입니다.

### CPU 환경에서는 무엇을 선택할까

CPU 환경에서는 결국 용도에 맞춰 선택할 수 있습니다.

| 우선순위 | 더 어울리는 선택 |
|---|---|
| 빠른 응답, 많은 요청, 작은 메모리 | Supertonic 3 |
| 레퍼런스와 가까운 음색과 음역 | Audio8 0.1B |
| 실시간보다 빠른 일괄 합성 | Supertonic 3 |
| 기다려도 유사도가 중요한 비동기 생성 | Audio8 0.1B |

하나가 모든 면에서 앞서는 것은 아니었습니다. Supertonic은 빠른 CPU TTS에 가깝고, Audio8은 속도를 양보해 화자를 더 직접적으로 복제하는 선택지였습니다.

## Supertonic의 품질 한계는 남았다

이번 Supertonic 구조로 GPU 비용은 없앴지만 어떤 목소리든 정확하게 복제할 수 있는 것은 아닙니다. Supertonic 자체가 레퍼런스를 직접 받는 Voice Cloning 모델은 아니기 때문입니다. 화자 특징을 잘 찾더라도 기본 모델이 그 음색을 낼 수 없으면 결과에는 차이가 남습니다.

실제로 비교해 보니 이런 문제가 남았습니다.

- 특이한 발성이나 속삭이는 음성은 일반적인 발성보다 유사도가 낮았습니다.
- 남성·여성의 음역이 크게 어긋나는 후보가 만들어지기도 했습니다.
- 후보 범위를 실제 목소리 주변으로 제한해도 기계음을 완전히 제거하지는 못했습니다.
- 레퍼런스에 배경 음악, 리버브, 다른 화자가 섞이면 결과가 빠르게 나빠졌습니다.

무엇보다 좋은 레퍼런스가 중요했습니다. 한 명이 말하는 8–15초 정도의 깨끗한 음성, 과도한 노이즈 제거가 없는 자연스러운 발성, 실제 서비스에서 사용할 말투와 가까운 구간이 안정적이었습니다.

## 정리하며

같은 레퍼런스로 만든 음성을 직접 들어보니 Audio8은 화자를 더 정확하게 따라왔고, Supertonic은 닮지 않은 부분이 분명 남았습니다. Supertonic이 레퍼런스를 직접 조건으로 사용하는 Voice Cloning 모델이 아니라는 점을 생각하면 자연스러운 한계였습니다.

대신 Supertonic은 작은 CPU에서 실시간보다 빠르게 음성을 만들었고, Audio8은 더 비슷한 목소리를 위해 훨씬 긴 대기 시간과 많은 메모리를 사용했습니다. GPU 없는 CPU 환경에서는 하나가 무조건 낫다고 정하기보다, 응답 속도와 화자 유사도 중 무엇이 중요한지에 따라 선택하는 편이 현실적이라는 걸 배웠습니다.
