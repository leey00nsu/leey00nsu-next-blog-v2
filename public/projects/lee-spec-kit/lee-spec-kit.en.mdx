## Project Overview

GitHub : [https://github.com/leey00nsu/lee-spec-kit](https://github.com/leey00nsu/lee-spec-kit)  
npm : [https://www.npmjs.com/package/lee-spec-kit](https://www.npmjs.com/package/lee-spec-kit)

Working with AI coding assistants, I found that different documentation structures and working conventions across projects required repeatedly sharing the same context.

I built a CLI to quickly introduce a specification-driven development workflow, with specifications, implementation plans, tasks, and decision records organized by feature.

As feature documents accumulated, past change records alone became insufficient for understanding the current codebase. I integrated OpenWiki to also maintain documents that describe the project’s structure and main flows based on the current implementation.

## Key Features

- **Specification-driven development**: Standardize the spec → plan → tasks → decisions workflow for each feature.
- **Feature-centered documentation**: Manage feature documents, progress, and next actions in a consistent structure.
- **OpenWiki integration**: Generate and synchronize documentation from the current codebase and validate its state and supporting evidence.

## Key Challenges and Solutions

### Repeated context sharing with AI coding assistants

When document locations, structures, and working conventions differ across projects, the same context must be explained repeatedly to AI coding assistants. I provided a shared documentation skeleton and templates so developers and agents can work from the same structure and conventions.

### Inconsistent feature development records

Scattered specifications, implementation plans, tasks, and decision records make it difficult to trace progress and the reasons for changes. I generated `spec.md`, `plan.md`, `tasks.md`, and `decisions.md` for each feature and managed them through a defined workflow, keeping what was implemented, why, and how traceable at the feature level.

### The gap between change history and the current codebase

Feature documents explain the background of changes, but understanding the current project structure can require reading across many records. I integrated OpenWiki to generate onboarding documents grounded in code, tests, and configuration. When enabled, the integration requires documentation synchronization and citation evidence checks before feature review. Feature documents explain the background of changes, while onboarding documents describe the current structure and main flows.
