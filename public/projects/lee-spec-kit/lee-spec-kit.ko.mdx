## 프로젝트 소개

GitHub : [https://github.com/leey00nsu/lee-spec-kit](https://github.com/leey00nsu/lee-spec-kit)  
npm : [https://www.npmjs.com/package/lee-spec-kit](https://www.npmjs.com/package/lee-spec-kit)

AI 에이전트와 함께 개발할 때 프로젝트마다 문서 구조와 작업 규칙이 다르면 매번 컨텍스트를 다시 전달해야 하는 문제가 있었습니다.

이를 줄이기 위해 Feature 단위로 스펙, 구현 계획, 태스크, 결정 기록을 남기는 Spec-driven Development 워크플로우를 프로젝트에 빠르게 적용할 수 있는 CLI를 만들었습니다.

이후 Feature 문서가 쌓이면서 과거 변경 기록만으로 현재 코드베이스의 모습을 파악하기 어려워지는 문제를 보완하기 위해 OpenWiki를 연동하고, 현재 구현을 기준으로 프로젝트 구조와 주요 흐름을 설명하는 문서를 함께 관리하도록 확장했습니다.

## 주요 기능

- **Spec-driven Development**: Feature마다 spec → plan → tasks → decisions 흐름을 표준화
- **Feature 중심 문서 관리**: 기능별 문서와 진행 상태, 다음 액션을 일관된 구조로 관리
- **OpenWiki 연동**: 현재 코드베이스 기반 기술 문서를 생성·동기화하고 문서 상태와 근거를 검증

## 핵심 문제와 해결

### AI 에이전트에 반복적으로 필요한 컨텍스트 전달

프로젝트마다 문서 위치와 구조, 작업 규칙이 다르면 AI 에이전트를 사용할 때 동일한 정보를 반복해서 설명해야 합니다. 프로젝트 문서의 기본 골격과 공용 템플릿을 제공해 사람과 에이전트가 동일한 구조와 규칙을 기준으로 작업하도록 만들었습니다.

### Feature 개발 과정의 일관성 부족

스펙·구현 계획·태스크·결정 기록이 서로 다른 위치에 흩어지면 기능의 진행 상태와 변경 이유를 추적하기 어렵습니다. Feature마다 `spec.md`, `plan.md`, `tasks.md`, `decisions.md`를 생성하고 정해진 흐름으로 관리해 무엇을 왜 어떻게 구현했는지 기능 단위로 추적할 수 있도록 했습니다.

### 과거 문서와 현재 코드베이스의 정보 차이

Feature 문서는 변경의 배경을 기록하는 데 유용하지만, 시간이 지나면 여러 문서를 읽어야 현재 프로젝트 구조를 파악할 수 있습니다. OpenWiki를 연동해 코드·테스트·설정에 근거한 온보딩 문서를 생성하고, 연동 활성화 시 기능 리뷰 전에 문서 동기화와 인용 근거 검증을 거치도록 했습니다. 변경 배경은 Feature 문서에서, 현재 구조와 주요 흐름은 온보딩 문서에서 찾아볼 수 있도록 역할을 구분했습니다.
